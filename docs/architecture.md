# Architecture

Notorium keeps framework entrypoints thin and pushes product logic into feature modules.

Audience: agents and contributors making structural, cross-boundary, or feature-module changes.

Related docs: [Docs Index](./README.md), [UI Conventions](./ui-conventions.md), [Agent Guide](../AGENTS.md), [README](../README.md)

## Source Layout

```text
src/
|-- app/                 Next.js App Router pages, layouts, API routes, and Server Actions
|   |-- (app)/           Authenticated pages
|   |-- actions/         Client-callable write boundary (Server Actions)
|   `-- api/             Client-callable read boundary (GET route handlers), uploads, cron
|-- components/          Feature UI, shared UI, the left menu (components/navbar), auth forms, and shadcn primitives
|-- features/            Feature queries, mutations, validation, mappers, and domain helpers
|   `-- planning/        Planning route helpers and planning-specific data shaping
|-- db/                  Drizzle schema and database client
|-- lib/                 Auth, server contracts, dates, editor, AI, email, rate limits, storage
`-- env.ts               Runtime environment validation
```

## Data Flow

```text
Server Component -> src/features/*/queries.ts -> Drizzle -> PostgreSQL
Client Component (write) -> src/app/actions/* -> validation/auth -> src/features/*/mutations.ts -> Drizzle
Client Component (read) -> src/lib/read-api/* -> GET src/app/api/* -> runUserReadRoute (auth/Zod) -> src/features/*/queries.ts
Scheduled Workflow -> src/app/api/* -> auth/config checks -> src/features/* service functions
```

## Ownership Boundaries

- `src/app/` owns framework routing, layouts, pages, API routes, and thin Server Actions.
- Mutation Server Actions run through `src/lib/server/action-runner.ts` (`runValidatedAction` / `runValidatedUserAction`): Zod-validated input, typed `{ success: true, ... } | ActionErrorResult` results for expected failures, and `runCatchingActionFailure` (`src/lib/server/action-failure.ts`) turning unexpected throws into `common.generic`. Each call passes a `<file>.<actionName>` log scope (for example `notes.editNote`) as its first argument. Failures are logged as `server_action_failed` with only that scope, error class, and driver code (never the message, which can carry SQL params); Next.js `redirect`/`notFound` are rethrown. There are no read Server Actions: Next.js runs actions one at a time per client (a slow mutation would queue every read behind it) and as uncacheable POSTs, so client-initiated reads are GET route handlers instead.
- Client reads go through GET route handlers under `src/app/api/` (`account/settings`, `assessments/planning-page`, `calendar/events`, `flashcards/{manage-page,ids,refine-groups,review-state,exam-cards,[flashcardId]}`, `mindmaps/[mindmapId]`, `notes/[noteId]`, `search`, `search/recent`, `subjects/options`, `subjects/[subjectId]/documents`). Each is a thin `runUserReadRoute` call (`src/lib/server/read-route.ts`): approved session (401), Zod-validated input from path params or `readSearchParams` (400), a `userId`-scoped `src/features/*/queries.ts` read, optional `notFoundErrorCode` for `null` results (404), and unexpected throws logged as `read_route_failed` via the shared `logServerFailure` (500, `common.generic`). Responses are `private, no-store` and encoded with `src/lib/read-api/read-payload.ts`, which tags `Date` values so they survive JSON the way RSC serialization kept them for Server Actions. Read routes never write: FSRS scheduler reads use `readFsrsSettings` in `src/features/flashcards/fsrs/settings-queries.ts` (defaults in memory when no row exists or persisted values are invalid), while mutations use `ensureFsrsSettings` in `settings-mutations.ts`, whose first-use insert is `ON CONFLICT DO NOTHING` plus a re-read so parallel first requests cannot fail on the unique `userId`. Components never `fetch` these URLs directly: typed fetchers in `src/lib/read-api/*` (`fetchReadApi` throws `ReadApiError`, `fetchReadApiResult` returns the `ActionErrorResult`, `fetchReadApiOrNull` maps 404 to `null`) own the URLs and redirect a 401 to `/login`.
- `src/components/` owns reusable and feature UI; shadcn primitives stay in `src/components/ui/`.
- `src/features/` owns product read/write logic, validation, mapping, constants, and feature-local types.
- Dense algorithms may live in feature subfolders, such as `src/features/flashcards/fsrs/`.
- Flashcard refine (streak detection, similar-card discovery, relate/merge mutations) lives in `src/features/flashcards/refine/`, with its Server Actions in `src/app/actions/flashcards-refine.ts`. The UI is a mode of the manage view in `src/components/flashcards/manage/` (refine results table, merge/improve dialogs, `use-refine-card-actions.ts`), entered from the manage toolbar AI dropdown. Merges snapshot source cards into the `flashcard_merge_log` table so lineage survives deletion.
- Flashcard review shortcut handling lives in `src/features/flashcard-review/shortcuts.ts`; the review UI calls that one hook instead of registering key listeners locally.
- Full-screen flashcard sessions mount through `ReviewScrollBoundary`, which portals the session and its auxiliary overlays outside the page layout and uses `react-remove-scroll` (also used by Radix dialogs) to coordinate nested scroll locks. The session shell owns the scrollable card area.
- Flashcard review logs keep historical flashcard and subject identifiers without a flashcard foreign key, so card/subject deletion does not rewrite the activity heatmap or remove FSRS optimization input. New review logs snapshot the prior scheduling state so the latest regular review can be undone transactionally; undo removes that log from activity and optimization history. The Home activity heatmap counts every review log for the user straight from `flashcard_review_log`, without joining flashcards.
- AI split replacement lives in `src/features/flashcards/split-mutation.ts` and deletes the source plus inserts every replacement in one transaction.
- Bulk flashcard mutations live in `src/features/flashcards/bulk-mutations.ts` to keep `mutations.ts` focused.
- Planning-specific URL and view helpers live in `src/features/planning/`.
- Subject hierarchy reads remain in `src/features/subjects/queries.ts` (the sidebar tree builder lives in `tree-queries.ts`). `getAllSubjectsWithPathsForUser` computes only `id`/`path` in its recursive CTE and takes the rows from Drizzle, so options keep the camelCase `SubjectEntity` shape and real `Date`s; atomic `::` path creation lives in `src/features/subjects/path-mutations.ts`, with the shared single-row insert in `subject-write.ts`. Intermediate auto-created path segments are general containers and the requested leaf owns the chosen kind. Academic-only read surfaces use `getOwnedAcademicSubjectFilters` so switching a subject to general hides attendance and assessment records without deleting them.
- Media uploads (note/flashcard/mindmap editor images) funnel through `src/features/attachments/mutations.ts`, then run `src/lib/media-storage/optimize-image.ts` before handing bytes to the storage provider (`src/lib/media-storage/provider.ts` → `vercel-blob-provider.ts`). The server upload path is therefore: validate → optimize → store. Image uploads (the editor and mindmap paths) transfer raw multipart bytes through the `POST /api/attachments/image` route handler into `uploadAttachmentImageForUser`, not a Server Action: Server Actions cap request bodies at 1 MB (below Vercel's 4.5 MB function-body ceiling, so it cannot just be raised), and multipart avoids base64's ~33% inflation. The shared client helper is `src/lib/attachments/upload-attachment-image.ts`. This route handler is the one sanctioned client-callable write endpoint outside Server Actions. `optimizeImageForStorage` re-encodes raster images to WebP with an EXIF-orientation fix and a max-dimension cap (sharp, `serverExternalPackages`), and falls back to the original bytes when sharp cannot decode them or WebP would not be smaller, so it never enlarges or corrupts an upload.
- The subject tree sidebar loads a subject's documents lazily through `src/components/subjects/tree/load-subject-documents.ts`. Each subject's state is `"loading"`, the list, or `"error"` (rendered as a "Couldn't load documents. Retry" row; collapsing and re-expanding also retries). Reads run in parallel now, so a per-subject request id keeps a stale response from overwriting a newer one.
- Notes and mindmaps are both subject-scoped and surfaced together in a subject's "Documents" area under `src/app/(app)/subjects/[id]/documents/` (`documents/notes/[noteId]/`, `documents/mindmaps/[mindmapId]/`). Document navigation comes from the global subject tree sidebar. The subject page is academic-only: a full-path breadcrumb plus the attendance and assessment summaries (`src/components/subjects/subject-detail-content.tsx`) — the documents, flashcards, and subfolders that used to live here are all managed in the sidebar instead. General subjects have no dashboard, so they are never a navigation target. `getSubjectPageHref` (`src/features/subjects/constants.ts`) is the single source of that rule — it returns a page href for academic subjects and `null` for general ones — and every surface that could link a subject routes through it: the sidebar tree label is inert text (expand via the chevron only), breadcrumb segments for general ancestors/subjects render unlinked (subject page and note/mindmap detail), document deletes for a general subject return home, direct general subject URL visits redirect home, and `getSearchDataForUser` omits general subjects from subject results (their notes/mindmaps stay searchable). `src/features/documents/` is a thin read layer that merges `src/features/notes` and `src/features/mindmaps` results into one recency-ordered list (`DocumentListItem`) used by the sidebar and the home dashboard. Note and mindmap detail pages do not render an in-page sidebar — document navigation comes from the global subject tree sidebar — so their editor/canvas spans the full content width. The per-document kebab (Edit/Delete/Generate/Copy/Export) is shared via `src/components/documents/document-row-menu.tsx` (the menu) and `use-document-row-dialogs.tsx` (a hook owning the dialog state + note copy, returning the row handlers and the dialog JSX); the tree sidebar (`src/components/subjects/tree/`) consumes it. Because the tree lives in the app shell, the authenticated layout (`src/app/(app)/layout.tsx`) loads subject options once and threads them with `aiEnabled` down to the tree so the "Generate flashcards" action works from any page.
- Mindmaps (`src/features/mindmaps/`) are scoped by `userId` and `subjectId` (mirroring notes). The branch-ordered canvas uses React Flow (`@xyflow/react`), loaded client-side, persists its node/edge graph as JSON in the `mindmap.data` column, and centralizes canvas keyboard shortcuts in `src/lib/mindmap/use-mindmap-shortcuts.ts`.
- The authenticated shell (`src/components/shared/app-layout-client.tsx`) renders the collapsible left menu (`src/components/navbar/`) beside the page content; there is no top navbar. Pages render a sticky breadcrumb top bar via `src/components/shared/page-top-bar.tsx` (`PageTopBar` and the matching `PageTopBarSkeleton` for `loading.tsx`), which is the location indicator and replaces per-page back links. Card/detail pages compose a sticky breadcrumb plus centered body through the shared `DetailPageLayout` (`src/components/shared/detail-page-layout.tsx`), which wraps `PageTopBar` over an `AppPageContainer` (default `max-w-5xl`, narrower per page via `maxWidth`: e.g. flashcard/admin `3xl`, assessment `4xl`, subject `5xl`); document workspaces (note, mindmap) stay full-width (`max-w-7xl`) and keep their own layout for zen mode. The root route (`src/app/(app)/page.tsx`) is the Home dashboard rendered inside the authenticated shell; it self-gates with `requireSession()` (signed-out users go to `/login`) and composes overview cards from existing feature queries (flashcards due, upcoming assessments, review activity, recent documents across subjects).
- `src/db/` owns the Drizzle schema, relations, and database client.
- `src/lib/` owns cross-cutting project helpers and wrappers for external services.
- `src/env.ts` owns runtime environment validation.

Cross-cutting services live behind project-owned helpers in `src/lib/`, including Better Auth, AI providers, email, media storage, and rate limiting.

The rich-text editor and read-only renderer (`src/components/shared/tiptap-editor.tsx` and `tiptap-renderer.tsx`) share their Tiptap extension sets through `src/lib/editor/build*Extensions()` helpers (tables, math). The editor exposes those commands through `tiptap-formatting-toolbar.tsx` and reuses the existing link dialog and private attachment upload path. Both surfaces must register the same extensions: Tiptap drops unknown nodes when parsing stored HTML, so math or tables present only in the editor would vanish in the renderer. Math nodes (KaTeX) serialize their LaTeX into a `data-latex` attribute, which `src/lib/editor/rich-text.ts` surfaces as text so equations stay searchable and within length limits.

## Enforced Boundaries

Three boundaries above are machine-checked, not just convention (see the Next.js Boundaries section in [AGENTS.md](../AGENTS.md)):

- Server Actions (`src/app/actions/*`) cannot import `@/db/index`; they go through `src/features/*`. Enforced by a `noRestrictedImports` override in `biome.json`.
- Components (`src/components/*`) cannot import `@/features/*/mutations`; writes flow through Server Actions. Enforced by the same rule. Server Components reading from `queries.ts` live under `src/app/*`, so they are unaffected. Client reads flow through `src/lib/read-api/*` to the GET route handlers.
- Read-only code cannot import write modules: Server Components under `src/app/(app)/**`, `src/features/**/queries.ts` and `*-queries.ts`, and every route under `src/app/api/` are barred from `@/features/**/mutations`, `*-mutations`, `*-mutation`, and `subject-write`. Enforced by a third `noRestrictedImports` override, so rendering a page or answering a GET can never create or repair rows. The override covers new routes by default; only the sanctioned writers are excluded (`attachments/image` upload, `auth`, and the scheduled `cron`, `notifications`, and `flashcards/fsrs` jobs).

A separate guard, `npm run check:size`, keeps files under 500 lines.
