# Architecture

Notorium keeps framework entrypoints thin and pushes product logic into feature modules.

Audience: agents and contributors making structural, cross-boundary, or feature-module changes.

Related docs: [Docs Index](./README.md), [UI Conventions](./ui-conventions.md), [Agent Guide](../AGENTS.md), [README](../README.md)

## Source Layout

```text
src/
|-- app/                 Next.js App Router pages, layouts, API routes, and Server Actions
|   |-- (app)/           Authenticated pages
|   |-- (auth)/          Signed-out pages (login, signup, password reset) sharing one centered layout
|   |-- actions/         Client-callable write boundary (Server Actions)
|   `-- api/             Client-callable read boundary (GET route handlers), uploads, AI chat stream, cron
|-- components/          Feature UI, shared UI, the left menu (components/navbar), auth forms, and shadcn primitives
|-- features/            Feature queries, mutations, validation, mappers, and domain helpers
|-- db/                  Drizzle schema and database client
|-- lib/                 Auth, server contracts, dates, editor, AI, email, rate limits, storage
`-- env.ts               Runtime environment validation
```

## Data Flow

```text
Server Component -> src/features/*/queries.ts -> Drizzle -> PostgreSQL
Client Component (write) -> src/app/actions/* -> validation/auth -> src/features/*/mutations.ts -> Drizzle
Client Component (read) -> src/lib/read-api/* -> GET src/app/api/* -> runUserReadRoute (auth/Zod) -> src/features/*/queries.ts
Study assistant (useChat) -> POST src/app/api/assistant/chat -> auth/Zod -> src/features/assistant/service.ts -> src/lib/ai/stream-chat.ts
Scheduled Workflow -> src/app/api/* -> auth/config checks -> src/features/* service functions
```

## Ownership Boundaries

- `src/app/` owns framework routing, layouts, pages, API routes, and thin Server Actions.
- Mutation Server Actions run through `src/lib/server/action-runner.ts` (`runValidatedAction` / `runValidatedUserAction`): Zod-validated input, typed `{ success: true, ... } | ActionErrorResult` results for expected failures, and `runCatchingActionFailure` (`src/lib/server/action-failure.ts`) turning unexpected throws into `common.generic`. Each call passes a `<file>.<actionName>` log scope (for example `notes.editNote`) as its first argument. Failures are logged as `server_action_failed` with only that scope, error class, and driver code (never the message, which can carry SQL params); Next.js `redirect`/`notFound` are rethrown. There are no read Server Actions: Next.js runs actions one at a time per client (a slow mutation would queue every read behind it) and as uncacheable POSTs, so client-initiated reads are GET route handlers instead.
- Server Actions revalidate only through `src/lib/server/revalidate-views.ts`, which maps a write to the views that show its data. `revalidateAppShell` refreshes the `(app)` layout (sidebar subject tree, document counts, due-card badges) and with it every page; use it for any subject, document create/move/delete, or flashcard write. Review grades and undo are the exception: they run on every keypress through the serial Server Action queue, so they skip revalidation and `use-app-shell-refresh-after-review.ts` calls `router.refresh()` once all review writes have landed and focus mode is closed, re-reading the review hub counts from the server at the same moment so hub and sidebar agree. `revalidateDocumentPage` covers document content writes the sidebar does not show. Actions never call `revalidatePath`/`revalidateTag` directly; lint-enforced by a `noRestrictedImports` override in `biome.json`.
- Client reads go through GET route handlers under `src/app/api/` (`account/settings`, `flashcards/{manage-page,contents,struggling,review-state,exam-cards,[flashcardId]}`, `mindmaps/[mindmapId]`, `notes/[noteId]`, `search`, `search/recent`, `subjects/options`, `subjects/[subjectId]/documents`). Each is a thin `runUserReadRoute` call (`src/lib/server/read-route.ts`): approved session (401), Zod-validated input from path params or `readSearchParams` (400), a `userId`-scoped `src/features/*/queries.ts` read, optional `notFoundErrorCode` for `null` results (404), and unexpected throws logged as `read_route_failed` via the shared `logServerFailure` (500, `common.generic`). Responses are `private, no-store` and encoded with `src/lib/read-api/read-payload.ts`, which tags `Date` values so they survive JSON the way RSC serialization kept them for Server Actions. The private-image streaming route `GET /api/attachments/blob` is separate from this JSON contract: it checks session and pathname ownership, then streams image bytes with storage headers and empty error responses. JSON read routes never write: FSRS scheduler reads use `readFsrsSettings` in `src/features/flashcards/fsrs/settings-queries.ts` (defaults in memory when no row exists or persisted values are invalid), while mutations use `ensureFsrsSettings` in `settings-mutations.ts`, whose first-use insert is `ON CONFLICT DO NOTHING` plus a re-read so parallel first requests cannot fail on the unique `userId`. Components never `fetch` these URLs directly: typed fetchers in `src/lib/read-api/*` (`fetchReadApi` throws `ReadApiError`, `fetchReadApiResult` returns the `ActionErrorResult`, `fetchReadApiOrNull` maps 404 to `null`) own the URLs and redirect a 401 to `/login`.
- `src/components/` owns reusable and feature UI; shadcn primitives stay in `src/components/ui/`.
- `src/features/` owns product read/write logic, validation, mapping, constants, and feature-local types.
- Dense algorithms may live in feature subfolders, such as `src/features/flashcards/fsrs/`.
- Flashcard refine (leech detection from `lapse_count` and recent review ratings) lives in `src/features/flashcards/refine/` and is read through `GET /api/flashcards/struggling`. The UI is a mode of the manage view in `src/components/flashcards/manage/` (refine results table, improve dialog, `use-refine-card-actions.ts`), entered from the manage toolbar `Refine cards` button; accepting an improvement saves through the `editFlashcard` Server Action.
- Flashcard review shortcut handling lives in `src/features/flashcard-review/shortcuts.ts`; the review UI calls that one hook instead of registering key listeners locally.
- Full-screen flashcard sessions mount through `ReviewScrollBoundary`, which portals the session and its auxiliary overlays outside the page layout and uses `react-remove-scroll` (also used by Radix dialogs) to coordinate nested scroll locks. The session shell owns the scrollable card area.
- Flashcard review logs keep historical flashcard and subject identifiers without a flashcard foreign key, so card/subject deletion does not rewrite the activity heatmap or remove FSRS optimization input. New review logs snapshot the prior scheduling state so the latest regular review can be undone transactionally; undo removes that log from activity and optimization history. The Home activity heatmap counts every review log for the user straight from `flashcard_review_log`, without joining flashcards.
- Bulk flashcard mutations live in `src/features/flashcards/bulk-mutations.ts` to keep `mutations.ts` focused.
- Flashcard copy (Markdown for AI chats and sharing) is client-side. `src/lib/clipboard/rich-text-markdown.ts` converts stored Tiptap HTML to Markdown with Turndown and the `@joplin/turndown-plugin-gfm` tables/strikethrough/task-list rules, after parsing it into an inert `DOMParser` document (no script runs, no image loads) and reshaping Tiptap's math, task-item, and list-paragraph markup, `flashcard-content.ts` formats cards, and `clipboard-writer.ts` starts the clipboard write inside the click with a promise-backed `ClipboardItem`, because Safari rejects writes that begin after an `await`. Cards not already in client state load through `fetchFlashcardContents`, which splits ids into requests of `LIMITS.flashcardContentsReadMax` (100) against `GET /api/flashcards/contents` to stay under URL length limits. `copyFlashcardsWithToast` (`src/components/flashcards/shared/`) is the one entry point the manage, detail, and review menus call; the manage view reaches it through `useFlashcardCopy`, which counts in-flight copies so the toolbar stays pending until all of them finish.
- Subject hierarchy reads remain in `src/features/subjects/queries.ts` (the sidebar tree builder lives in `tree-queries.ts`). `getAllSubjectsWithPathsForUser` computes only `id`/`path` in its recursive CTE and takes the rows from Drizzle, so options keep the camelCase `SubjectEntity` shape and real `Date`s; atomic `::` path creation lives in `src/features/subjects/path-mutations.ts`, with the shared single-row insert in `subject-write.ts`.
- Media uploads (note/flashcard/mindmap editor images) funnel through `src/features/attachments/mutations.ts`, then run `src/lib/media-storage/optimize-image.ts` before handing bytes to the storage provider (`src/lib/media-storage/provider.ts` → `vercel-blob-provider.ts`). The server upload path is therefore: validate → optimize → store. Image uploads (the editor and mindmap paths) transfer raw multipart bytes through the `POST /api/attachments/image` route handler into `uploadAttachmentImageForUser`, not a Server Action: Server Actions cap request bodies at 1 MB (below Vercel's 4.5 MB function-body ceiling, so it cannot just be raised), and multipart avoids base64's ~33% inflation. The shared client helper is `src/lib/attachments/upload-attachment-image.ts`. This route handler is the one sanctioned client-callable write endpoint outside Server Actions. `optimizeImageForStorage` re-encodes raster images to WebP with an EXIF-orientation fix and a max-dimension cap (sharp, `serverExternalPackages`), and falls back to the original bytes when sharp cannot decode them or WebP would not be smaller, so it never enlarges or corrupts an upload.
- AI calls share one layer in `src/lib/ai/`: `config.ts` (instance OpenRouter settings, including one reasoning effort that defaults to `none`), `provider.ts` (model factory that applies that effort as `reasoning.effort` to every call), `generate-structured.ts` (Zod-typed one-shot output), `stream-chat.ts` (UI message stream `Response` for `useChat`; mid-stream errors are logged as `ai_chat_failed` and reach the client only as the SDK's generic error; an optional `sessionId` becomes OpenRouter's `session_id` so a chat's turns stay on one provider's prompt cache), `user-ai-access.ts` (`acquireUserAiSettings` resolves settings and then spends one unit of a per-user daily limit; `runUserAiTask` folds unconfigured AI, limits, and throws into typed `errorCode` results for non-streaming tasks, logging throws as `ai_task_failed` under the task's `logScope`), `prompt-rules.ts` (shared prompt fragments such as `MATH_RULE`), and `plain-text-rich-text.ts` (isomorphic conversion of AI plain text with lists, code fences, and LaTeX into Tiptap HTML). Feature AI code (`src/features/flashcards/ai*.ts`, `src/features/assistant/`) owns only prompts, schemas, and result shaping. Generated content follows the user's language: chat replies match the user's messages, and flashcard generation and improvement write in the language of the source material or cards.
- The study assistant lives in `src/features/assistant/` (request schema, system prompt, `streamAssistantReplyForUser`) and `src/components/assistant/` (`StudyAssistant` launcher mounted by the app shell when `aiEnabled`, a lazily loaded presentation-only `AssistantPanel` backed exclusively by the shell-owned `AssistantWorkspaceProvider` on `@ai-sdk/react` `useChat`, and `assistant-chat-transport.ts`, which trims history to `LIMITS.assistantMaxMessages`, sends the `useChat` id as `chatId` for cache routing, and resolves route errors to messages). The system prompt and tool list stay byte-identical across a chat's turns so providers can serve them from the prompt cache; put per-turn context after prior history and before the latest user message, not in the instructions. It streams through `POST /api/assistant/chat`, the one sanctioned streaming AI endpoint outside Server Actions: actions run one at a time per client (a reply in flight would queue every write behind it) and cannot stream. The route writes nothing; it authenticates, validates the whole non-persistent chat with Zod (user/assistant text, step markers, answered creation/edit proposals and library searches, and optional size-limited draft or study context; pending or failed tool calls are dropped), and delegates, answering `ActionErrorResult` bodies with 400/401/429/503/500. Chats live only in client memory. Assistant tools live in `src/features/assistant/tools.ts` and reach `streamText` through `streamChatResponse`'s `tools` option, typed into `AssistantUIMessage` (`src/features/assistant/types.ts`). `proposeFlashcards` has no `execute` and carries all of a reply's cards (1–5) in one call, since many models make only one tool call per reply: the call ends the reply, `AssistantFlashcardProposal` renders it with a subject preselected from the user's subject paths (the service reads them into the system prompt), and the user's Create goes through the `createFlashcard` Server Action; per-card outcomes are tracked by `use-flashcard-proposal-outcomes.ts` and stored with `addToolOutput`; before each send, cards still open are recorded as `skipped` (restorable in the UI), so the model always gets a result for every proposal. Prefer this propose-then-confirm shape for future write tools. `buildAssistantTools` takes the read-only `searchLibrary` function from the service (`searchLibraryForUser` in `src/features/search/library-queries.ts`, bound to the session user), the one tool with `execute`: replies run up to two model steps (`maxModelSteps`) with the same tool list on both, so the answer step stays on the prompt cache; the prompt allows one search per reply. Its contract lives in `library-search-contract.ts`: a few model-chosen terms in, at most 4 hits per kind with 120-character excerpts out, and `toModelOutput` gives the model a compact quoted list without ids while `AssistantLibraryResults` builds links from the ids. Search failures are logged and reach the model as a fixed message. Chat history keeps `step-start` markers, since `convertToModelMessages` splits a reply into steps at them and a search result would otherwise follow the answer it fed. A tool that writes from the route instead must call the same `src/features/*/mutations.ts` functions the Server Actions use, revalidate through `revalidate-views.ts`, and get an explicit `biome.json` exclusion.
- The subject tree sidebar loads a subject's documents lazily through `src/components/subjects/tree/load-subject-documents.ts`. Each subject's state is `"loading"`, the list, or `"error"` (rendered as a "Couldn't load documents. Retry" row; collapsing and re-expanding also retries). Reads run in parallel now, so a per-subject request id keeps a stale response from overwriting a newer one.
- The assistant is one global collapsible sidebar: `AssistantAppFrame` reserves desktop space, and `AssistantSurfaceHost` portals its presentation into full-screen review or flashcard dialogs so focus/scroll locks include chat. Hosts stack and restore the previous host on close; all overlays retain the same named layer. The shell owns conversation, composer, and open state, so moving the presentation never resets the chat. Flashcard editor dialogs use a viewport-sized focus boundary around the centered form and global sidebar; mobile opens chat over the editor.
- Flashcard draft editing registers the active form through `use-active-flashcard-editor.ts`; per-send snapshots carry an ephemeral session id and revision, not a database write target. `proposeFlashcardEdits` has no execute function: completed proposals are routed to their original revision and reviewed per field inside the editor. Accepted replacements go through React Hook Form; existing Server Actions (or detail auto-save) save them. Draft context follows prior history as background in the latest user turn, before the actual user message, never in system instructions. The user message remains last so draft context does not replace the question; prompt and tool instructions reserve edit proposals for explicit requests to change the card. Image locations are replaced with placeholders before sending; replacements restore only original images, sanitize, convert plain-text output and dollar-delimited math in HTML text nodes (excluding code and existing math), and normalize through the shared read-only editor schema. Review decorations never enter form values or persisted HTML. Late/mismatched replies become stale outcomes; unresolved fields become skipped before follow-ups or editor teardown. The only single-back AI path left is refine's "Improve" (`improveFlashcardBack` → `src/features/flashcards/back-improvement.ts`); generating a back from the front alone was removed with the editor buttons.
- Notes and mindmaps are both subject-scoped and surfaced together in a subject's "Documents" area under `src/app/(app)/subjects/[id]/documents/` (`documents/notes/[noteId]/`, `documents/mindmaps/[mindmapId]/`). Document navigation comes from the global subject tree sidebar. Subjects are folders with no page of their own, so they are never a navigation target: the sidebar tree label is inert text (expand via the chevron only), subject breadcrumb segments on note/mindmap detail render unlinked, document deletes return home, `/subjects/:id` redirects home through `redirects()` in `next.config.ts`, and `getSearchDataForUser` returns no subject results (notes and mindmaps still match their subject's name). `src/features/documents/` is a thin read layer that merges `src/features/notes` and `src/features/mindmaps` results into one recency-ordered list (`DocumentListItem`) used by the sidebar and the home dashboard. Note and mindmap detail pages do not render an in-page sidebar — document navigation comes from the global subject tree sidebar — so their editor/canvas spans the full content width. The per-document kebab (Edit/Delete/Copy/Export) is shared via `src/components/documents/document-row-menu.tsx` (the menu) and `use-document-row-dialogs.tsx` (a hook owning the dialog state + note copy, returning the row handlers and the dialog JSX); the tree sidebar (`src/components/subjects/tree/`) consumes it. AI flashcard creation from documents uses the study assistant’s live context and `proposeFlashcards`; there are no dedicated document-generation dialogs or Server Actions. Subject options are no longer loaded by the authenticated layout for document menus.
- Mindmaps (`src/features/mindmaps/`) are scoped by `userId` and `subjectId` (mirroring notes). The branch-ordered canvas uses React Flow (`@xyflow/react`), loaded client-side, persists its node/edge graph as JSON in the `mindmap.data` column, and centralizes canvas keyboard shortcuts in `src/lib/mindmap/use-mindmap-shortcuts.ts`.
- The authenticated shell (`src/components/shared/app-layout-client.tsx`) renders the collapsible left menu (`src/components/navbar/`) beside the page content; there is no top navbar. Pages render a sticky breadcrumb top bar via `src/components/shared/page-top-bar.tsx` (`PageTopBar` and the matching `PageTopBarSkeleton` for `loading.tsx`), which is the location indicator and replaces per-page back links. Card/detail pages compose a sticky breadcrumb plus centered body through the shared `DetailPageLayout` (`src/components/shared/detail-page-layout.tsx`), which wraps `PageTopBar` over an `AppPageContainer` (default `max-w-5xl`, narrower per page via `maxWidth`: e.g. flashcard/admin `3xl`); document workspaces (note, mindmap) stay full-width (`max-w-7xl`) and keep their own layout for zen mode. The root route (`src/app/(app)/page.tsx`) is the Home dashboard rendered inside the authenticated shell; it self-gates with `requireSession()` (signed-out users go to `/login`) and composes overview cards from existing feature queries (flashcards due, review activity, recent documents across subjects).
- `src/db/` owns the Drizzle schema, relations, and database client. Text search is accent- and case-insensitive through `immutable_unaccent()`, an IMMUTABLE SQL wrapper over the `unaccent` extension created by the custom migration `drizzle/0070_unaccent_search.sql` (Drizzle cannot generate extensions or functions; it needs no superuser, so it runs on Neon). The GIN trigram indexes in `src/db/schema.ts` (`unaccentTrigramIndex`) cover `immutable_unaccent(column)`, so queries must build matches with `src/features/search/match-sql.ts` (`foldedContains`, `buildTermSearch`), which wraps columns the same way; any other wrapping skips the indexes. Highlighting and node-label matching fold text the same way on the client with `src/lib/search/fold.ts`.
- `src/lib/` owns cross-cutting project helpers and wrappers for external services.
- `src/env.ts` owns runtime environment validation.

Cross-cutting services live behind project-owned helpers in `src/lib/`, including Better Auth, AI providers, email, media storage, and rate limiting.

The rich-text editor and read-only renderer (`src/components/shared/tiptap-editor.tsx` and `tiptap-renderer.tsx`) share their Tiptap extension sets through `src/lib/editor/build*Extensions()` helpers (tables, math). The editor exposes those commands through `tiptap-formatting-toolbar.tsx` and reuses the existing link dialog and private attachment upload path. Both surfaces must register the same extensions: Tiptap drops unknown nodes when parsing stored HTML, so math or tables present only in the editor would vanish in the renderer. Math nodes (KaTeX) serialize their LaTeX into a `data-latex` attribute, which `src/lib/editor/rich-text.ts` surfaces as text so equations stay searchable and within length limits.

## Enforced Boundaries

Three boundaries above are machine-checked, not just convention (see the Next.js Boundaries section in [AGENTS.md](../AGENTS.md)):

- Server Actions (`src/app/actions/*`) cannot import `@/db/index`; they go through `src/features/*`. Enforced by a `noRestrictedImports` override in `biome.json`.
- Components (`src/components/*`) cannot import `@/features/*/mutations`; writes flow through Server Actions. Enforced by the same rule. Server Components reading from `queries.ts` live under `src/app/*`, so they are unaffected. Client reads flow through `src/lib/read-api/*` to the GET route handlers.
- Read-only code cannot import write modules: Server Components under `src/app/(app)/**`, `src/features/**/queries.ts` and `*-queries.ts`, and every route under `src/app/api/` are barred from `@/features/**/mutations`, `*-mutations`, `*-mutation`, and `subject-write`. Enforced by a third `noRestrictedImports` override, so rendering a page or answering a GET can never create or repair rows. The override covers new routes by default; only the sanctioned writers are excluded (`attachments/image` upload, `auth`, and the scheduled `cron` and `flashcards/fsrs` jobs).

A separate guard, `npm run check:size`, enforces 500-line source and 800-line test limits; `src/db/schema.ts` is exempt.

### Study surface context

`useStudyContext` registers live review/exam, note, and mindmap snapshots with the shell workspace. Editor drafts take precedence; mounted study surfaces stack and restore on teardown. The request accepts either the existing draft or a validated `StudyContext` union, never both. Context precedes the latest question as untrusted background; system instructions and tools stay stable. Review snapshots omit unrevealed backs. Document snapshots use current client edits, cap readable content at 12,000 characters, and mark partial excerpts. Notes replace explicit images and renderer-recognized image paragraphs with placeholders before converting to Markdown; mindmaps serialize root-first labels and edges with explicit arrow directions, without positions or attachment locations. Document zen mode mounts the existing assistant surface host inside its immersive boundary and reserves desktop sidebar space. No new reads, writes, endpoints, or AI requests are introduced.
